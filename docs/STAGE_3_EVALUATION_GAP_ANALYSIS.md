## 2. Forensic Analysis of Stage 2B Implementation

### 2.1 What Stage 2B Actually Implemented
* `[VERIFIED FACT]`: In `ml/experiments/run_baseline_experiments.py`, the AI4I 2020 dataset ($N=10,000$, SHA-256: `dc6630cd9b1f0f853922fad78a1b6436570d3f1ec863f1dd5c4340ac56bc8a8e`) was partitioned into a **single 80/20 stratified holdout split**:
  - Training partition: 8,000 rows ($N_{\text{pos}} = 271$, $3.39\%$, SHA-256 hash: `67471419f2a9a808e27a300667946f2927d7d3b160ea1e4675cabd17cdfc66e8`).
  - Test partition: 2,000 rows ($N_{\text{pos}} = 68$, $3.40\%$, SHA-256 hash: `8e8fef98bdc3f3d6acd0abe46e342ff4fb29d336aaa77143a3e84b2fef10073b`).
* `[VERIFIED FACT]`: Eight baseline models (EXP-001 through EXP-008 across Configurations A and B) were fitted on the 8,000-row training set and directly evaluated on the 2,000-row test partition.
* `[VERIFIED FACT]`: The serialized artifacts `EXP-004_xgboost_config_a.joblib` and `EXP-008_xgboost_config_b.joblib` were trained with `n_estimators=100`, `max_depth=5`, `learning_rate=0.05`, and `scale_pos_weight=28.520295`.
* `[VERIFIED FACT]`: The baseline models output raw XGBoost probabilities generated by the tree ensemble's internal logistic sigmoid link. No post-hoc probability calibrator (Platt scaling or isotonic regression) was fitted or serialized.

### 2.2 Which PRD Requirements Were Omitted in Stage 2B
* `[PRD REQUIREMENT]` (§10.1.4): *"Validate and split (stratified, locked test) → repeated stratified CV with a fixed search budget → choose by CV PR-AUC → calibrate (isotonic or Platt) on the validation partition → choose the threshold by a configured cost ratio (placeholder, Appendix E) → evaluate once on the test partition with CIs, curves and SHAP summary → registration gate."*
* `[VERIFIED FACT]`: **Repeated stratified cross-validation was completely omitted** during Stage 2B. Model selection was performed post-hoc on the holdout test set.
* `[VERIFIED FACT]`: **Validation-partition calibration was omitted**.
* `[VERIFIED FACT]`: **Cost-ratio threshold optimization was omitted**. Stage 2B recorded metrics at default $\tau = 0.50$ and subsequently applied an empirical heuristic $\tau = 0.45$.
* `[PRD REQUIREMENT]` (§10.1.5): *"Both AI4I configurations use identical splits, folds, search budgets and metrics... report each configuration's metrics with bootstrap CIs on the same test partition, plus paired bootstrap differences... and paired fold-wise differences on validation."*
* `[VERIFIED FACT]`: Paired fold-wise differences were not computed because CV folds were not generated. Bootstrap confidence intervals were omitted from `baseline_results.json` (though subsequently fabricated in model cards).

## 3. Structural Evaluation Protocol Gaps

### 3.1 Why Historical Baselines Cannot Be Claimed as Repeated-CV Results
* `[VERIFIED FACT]`: The baseline metrics in `baseline_results.json` reflect a single realization of an 80/20 train/test split.
* `[METHODOLOGICAL RECOMMENDATION]`: A single train/test split estimate has high sampling variance on rare-event failure data ($N_{\text{pos}} = 68$ in test). In contrast, repeated stratified cross-validation (e.g. 5x5 or 10x10 repeated CV) averages performance across multiple fold realizations, providing an estimate of the modeling procedure's generalization stability. Conflating a single-split evaluation with repeated CV results violates statistical rigor.

### 3.2 Why the Historical Test Set Cannot Serve as an Untouched Confirmatory Set
* `[VERIFIED FACT]`: The 2,000-sample test partition has already been accessed and evaluated across all 8 baseline models.
* `[METHODOLOGICAL RECOMMENDATION]`: In statistical testing, an evaluation set is confirmatory **only if the hypothesis, model, and decision threshold were pre-specified without prior exposure to that test set**. Because the historical test set was examined during baseline exploration, any subsequent evaluation of calibrated models or candidate models on this same partition is **historically non-independent and exploratory**. 
* `[METHODOLOGICAL RECOMMENDATION]`: A genuinely confirmatory generalization evaluation requires a completely fresh, unobserved external dataset.

### 3.3 Why a 6,000/2,000 Calibration Split Creates New Model Identities
* `[VERIFIED FACT]`: The historical baselines (`EXP-004`, `EXP-008`) were fitted on 8,000 observations with 271 failures.
* `[METHODOLOGICAL RECOMMENDATION]`: Partitioning the 8,000-sample development pool into 6,000 sub-train and 2,000 validation observations reduces base estimator training data by $25\%$ ($N_{\text{sub,pos}} = 203$, $N_{\text{sub,neg}} = 5,797$).
* `[METHODOLOGICAL RECOMMENDATION]`: An XGBoost model trained on 6,000 rows has different optimal tree structures, split thresholds, and leaf values than one trained on 8,000 rows. Therefore, the resulting model cannot be claimed as an "addendum" or "calibration patch" to `EXP-004`/`EXP-008`. It is a **new model identity** and must be assigned a distinct artifact identifier (e.g., `EXP-004-CAL`, `EXP-008-CAL`).

### 3.4 Why Calibration Must Operate on Raw XGBoost Margins
* `[VERIFIED FACT]`: Neither `XGBClassifier` nor a scikit-learn `Pipeline` terminating in `XGBClassifier` implements `decision_function`.
* `[VERIFIED FACT]`: When scikit-learn's `CalibratedClassifierCV` is wrapped around such an estimator, it detects `hasattr(estimator, 'decision_function') == False` and falls back to extracting `predict_proba(X)[:, 1]`.
* `[METHODOLOGICAL RECOMMENDATION]`: Standard `CalibratedClassifierCV` fits a sigmoid on top of probabilities that have already undergone logistic transformation inside XGBoost:
  $$P_{\text{cal}} = \sigma\left(a \cdot P_{\text{raw}} + b\right)$$
  This double-sigmoid distortion restricts the input domain of the calibrator to $[0, 1]$ rather than $(-\infty, +\infty)$.
* `[METHODOLOGICAL RECOMMENDATION]`: Genuine Platt scaling requires extracting the unconstrained tree margin $f(x) \in (-\infty, +\infty)$ via `booster.predict(..., output_margin=True)` and fitting:
  $$P(Y=1 \mid f(x)) = \sigma\left(w \cdot f(x) + c\right) = \frac{1}{1 + \exp\left(-(w \cdot f(x) + c)\right)}$$
  with the explicit monotonicity constraint $w > 0$.

### 3.5 Why Calibration and Threshold Metrics on the Validation Partition are In-Sample
* `[VERIFIED FACT]`: The 2,000-sample validation partition is used to fit the calibration parameters ($w$ and $c$) and to search for the cost-minimizing decision threshold $\tau_{\text{val}}^*$.
* `[METHODOLOGICAL RECOMMENDATION]`: Because the parameters $w$, $c$, and $\tau_{\text{val}}^*$ are optimized directly on this partition, any Brier score, ECE, reliability diagram, precision, recall, or operational cost calculated on this partition represents an **in-sample optimization diagnostic**, not out-of-sample generalization.
* `[METHODOLOGICAL RECOMMENDATION]`: These metrics must be clearly documented as "Validation In-Sample Fitting Diagnostics" and never represented as proof of generalization.

### 3.6 What Additional Validation Design is Needed for Independent Calibration Assessment
* `[METHODOLOGICAL RECOMMENDATION]`: To independently evaluate calibration without relying on the historical test set or in-sample validation diagnostics, one of two designs is required:
  1. **Nested Cross-Validation with Inner Calibration:** In an outer $K$-fold CV loop, each outer fold evaluates an estimator and calibrator fitted strictly within the inner loop, producing pooled out-of-fold calibrated probabilities.
  2. **External Industrial Benchmark:** Evaluating on an independent machine dataset with verified ground truth failure annotations.

### 3.7 How Stage 3 Must Compare Baseline and Candidate Models
* `[PRD REQUIREMENT]` (§10.1.5): Baseline models establish the benchmark; candidate models must beat the baseline on PR-AUC and Brier score simultaneously.
* `[METHODOLOGICAL RECOMMENDATION]`: Candidate models cannot be compared against uncalibrated historical baselines, because calibration artificially reduces Brier score.
* `[METHODOLOGICAL RECOMMENDATION]`: In Stage 3, both baselines (Logistic Regression, Decision Tree, Random Forest, XGBoost) and advanced candidates (LightGBM, CatBoost, feature-engineered pipelines) must be evaluated under the **exact same repeated cross-validation, identical fold indices, identical calibration method, and identical threshold rules**.
